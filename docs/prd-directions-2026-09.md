# 能量日誌 PRD 方向草案（2026-09）

> 來源：`Personal Knowledge/0-Inbox/隨想靈感和筆記/2026-09-06 兩個矛盾：能量日誌的刻意減量與 Token 額度帶來的知識複利.md`
> 狀態：方向草案，尚未進入規格。本文件目的是把隨想卡裡的觀察轉成「可以開規格的問題陳述、判準、功能候選與階段順序」。

---

## 0. 一句話

**在登記密度從 100% 降到約 50% 的新水位下，讓系統仍然看得見趨勢、分得清「刻意不記」與「不小心停掉」，而且不增加任何壓迫感。**

---

## 1. 問題陳述

### 1.1 資料事實（2026-09-06 從 CSV 統計）

| 月份 | 已登記 / 可登記天數 | 比例 |
|---|---|---|
| 6 月 | 12 / 12 | 100% |
| 7 月 | 17 / 31 | 54.8% |
| 8 月 | 16 / 31 | 51.6% |
| 9 月（至 9/6） | 0 / 6 | 0% |

7、8 月幾乎持平，代表這是**刻意調節到新水位後穩住**，不是衰退曲線。但 9 月至今為 0，而系統在這 6 天內沒有發出任何訊號。

### 1.2 三個核心問題

**P1. 刻意與漏掉在資料上無法區分**
「我今天選擇不記」與「我忘了」都是空白列。系統沒有欄位承載這個意圖，因此任何後續分析（包含這份卡片本身的統計）都無法確認「刻意減量」這個說法。這是三個提案功能之外、更根本的缺口。

**P2. 失效是安靜的**
從「刻意減量」滑到「實際停用」的過程中，沒有任何時間點會出聲。這是 [[安靜地壞掉：不報錯的失效模式]] 在個人系統上的實例。順帶：目前 `submitForm()` 用 `no-cors` 送出後直接顯示成功，寫入失敗也不會被發現，是同一種形狀。

**P3. 50% 密度下，逐日刻度失去訊噪比**
[[能量日誌的個人改變機制]] 的層 1（可見化）原本靠逐日數字成立。隔天一記之後，單日數字沒有比較基準，必須聚合到週才讀得出趨勢。週回顧不是加值功能，而是**維持層 1 有效性的必要補償**。

### 1.3 不是問題的東西（刻意排除）

- 登記比例本身不是問題。50% 是使用者自己選的水位。
- 「回饋不夠快」暫不視為缺陷。[[為什麼追蹤能量]] 的立論就是長期趨勢，把設計特性讀成缺陷有風險（見第 6 節假說）。

## 2. 設計判準（開規格前必須通過）

> **系統只補「訊號」，不補「義務」。**

具體化為五條，每一個功能都要能對照回答：

| # | 判準 | 違反的例子 |
|---|---|---|
| C1 | 不呈現達成率、連續天數、streak | 「本月登記 52%」「連續 3 天未登記」 |
| C2 | 提醒不可連續、不可每日 | 每天晚上跳通知 |
| C3 | 補登不能有「欠債感」 | 列出所有未填日期要求逐一補齊 |
| C4 | 使用者可以一鍵表態「這幾天我選擇不記」，且該表態被視為正常資料 | 只能填分數或留空 |
| C5 | 任何新增的「看」的功能，只呈現趨勢與相對變化 | 用紅色標示低於平均的週 |

補充：Sheet 側欄目前已有「總天數／高壓日／平均思緒分數」等摘要欄，這些是分析用，不應搬進前端。

## 3. 現況架構與限制

| 元件 | 現況 | 對新功能的限制 |
|---|---|---|
| 前端 | 單一 `index.html`，GitHub Pages | 無框架、無建置流程，所有功能都是 vanilla JS 增量 |
| 後端 | Google Apps Script Web App | `doGet(?date=)` 只回單筆；`doPost` 寫入或覆蓋同日期 |
| 寫入回饋 | `fetch(..., {mode:'no-cors'})` | 讀不到回應，成功與否無法判斷 |
| 資料 | Google Sheet，2026 全年日期列已預填，活動欄預設 FALSE | 「未登記」= 分數欄為空；新增欄位要同時改 Sheet 與 `.gs` |
| 日期 | 前端寫死為台灣時區今天 | 補登需開放日期選擇 |
| 排程 | 無 | 提醒若要主動推送，需 GAS 時間觸發器加 email 或其他通道 |

## 4. 功能候選

每項標注：對應問題、對應層、判準風險、實作所需改動。

### F0. 「今天選擇不記」標記 ⭐ 最根本

- **對應**：P1。讓刻意與漏掉在資料上可分。
- **形式**：表單上一顆低調的按鈕「今天不記，只留個記號」。送出後該日期列寫入 `跳過=TRUE`，分數欄維持空白。
- **判準**：C4 直接滿足。注意不可在週回顧中把「跳過」畫成負面狀態。
- **改動**：Sheet 新增欄位 `跳過`；`.gs` 的 `doPost` 接受該欄位；前端加按鈕與一支獨立的送出函式。
- **範圍外**：不做「為什麼不記」的原因欄。多一個欄位就多一份義務。

### F1. 週回顧（趨勢，不呈現達成率）⭐ 假說檢驗的主體

- **對應**：P3。層 1 可見化在新密度下的補償。
- **形式**：表單頂部或獨立區塊，顯示最近 4 週的三個分數週平均折線或小型長條，加上活動勾選的週次數。「跳過」與「空白」都不畫，只用淡色標記該週有幾天有資料。
- **判準**：C1、C5。不出現百分比、不出現「未登記」字樣、不上色警示。
- **改動**：`.gs` 新增 `doGet(?from=&to=)` 或 `?weeks=4` 回傳區間資料；前端新增渲染函式。
- **開放問題**：週平均在一週只有 1 到 2 筆時是否顯示？建議門檻 2 筆以上才畫點，否則留空但不解釋。

### F2. 補登前幾天

- **對應**：降低摩擦，避免一次漏記引發整段放棄。
- **形式**：日期列可點，開啟一個只含最近 7 天的選擇器。選擇後沿用既有 `loadTodayRecord` 流程預填該日資料。
- **判準**：C3。不列出「哪些天沒填」，只是允許改日期。
- **改動**：`getTaiwanDate()` 改為可被覆寫；`loadTodayRecord` 與 `submitForm` 改吃選定日期。後端不需改動，`?date=` 已支援任意日期。

### F3. 沉默提醒（第二階段，A/B 後決定）

- **對應**：P2。讓失效會叫。
- **形式**：兩個層級可選。
  - 被動版：打開頁面時，若最近一筆（含跳過）距今超過 N 天，顯示一行文字「上次留記號是 X 天前」。不彈窗、不上色。
  - 主動版：GAS 時間觸發器每日檢查，超過 N 天且本週尚未通知過，發一封 email。
- **參數**：N 建議 5 到 7 天。同一次沉默期只通知一次。
- **判準**：C2 是硬約束。任何「每日」變體都不做。
- **為什麼放第二階段**：見第 6 節。與 F1 同時上線會分不出哪個起作用。

### F4. 寫入結果可驗證（技術債，順帶處理）

- **對應**：P2 的技術版本。
- **形式**：`.gs` 的 `doPost` 回傳 JSON 並加上正確的 CORS header；前端改用可讀取回應的 fetch，失敗時顯示錯誤而非假成功。
- **理由**：這是能量日誌自己的「安靜地壞掉」。修這個不需要產品決策，可以與 F0 一起改 `.gs` 時順手處理。

## 5. 階段規劃

```
Phase 1（觀察期起點）        Phase 2（視 Phase 1 結果）
F0 跳過標記                   F3 提醒（被動版優先）
F1 週回顧
F2 補登
F4 寫入驗證
```

**Phase 1 觀察窗**：上線後 4 到 6 週。以 9/15 為第一個檢查點（卡片自訂：若 9/15 仍為 0 筆，「刻意減量」需修正為「已停用」）。

**Phase 2 觸發條件**：Phase 1 結束時，若「有資料的天數比例」（登記 + 跳過）沒有回到 7、8 月水位（約 50%），再加 F3。若已回升，F3 不做，或只做被動版。

## 6. 可檢驗的假說

卡片第四節提出：被抗拒的可能不是依賴系統，而是「系統向我索取」這個方向，也就是回饋迴圈太長。

**檢驗設計**：先上 F1 週回顧（縮短有效回饋迴圈），不上 F3 提醒。若假說成立，登記比例應自行回升。

| 結果 | 解讀 | 下一步 |
|---|---|---|
| 比例回升到約 50% 以上 | 回饋迴圈長度是主因 | 不做 F3 |
| 比例不動，但「跳過」標記有在用 | 使用者仍在系統裡，只是不想填分數 | 重新檢視三個分數是否太多 |
| 比例不動，跳過也沒用 | 不是回饋問題，是進入頻率問題 | 上 F3 被動版 |

⚠️ 樣本是 1 個人、2 個系統、3 個月。結果只能當個人層面的訊號，不能外推。

## 7. 成功指標（觀察者側，不呈現給使用者）

這些數字只在 Sheet 或事後分析看，**不進前端**，否則違反 C1。

| 指標 | 定義 | 為什麼 |
|---|---|---|
| 有資料天數比例 | （登記 + 跳過）/ 可登記天數，按月 | 取代「達成率」；跳過算有資料 |
| 跳過佔比 | 跳過 / 有資料天數 | 檢驗 F0 是否被使用，以及刻意減量的真實比例 |
| 最長沉默期 | 連續無任何資料的最長天數 | P2 的直接量測 |
| 補登比例 | 日期 ≠ 送出日的筆數比例 | 檢驗 F2 有無降低摩擦 |
| 週回顧開啟 | 若實作為可展開區塊，記一個計數 | 選配；不想加追蹤就跳過 |

## 8. 非目標與反模式

- 不做每日推播、不做 streak、不做完成度圓環。
- 不做「補齊所有缺漏」的清單視圖。
- 不做新的分數維度。三個分數已是使用者選定的最小集合。
- 不把 Sheet 側欄摘要（總天數、高壓日）搬到前端。
- 不做多使用者或帳號系統。

## 9. 開放問題

1. **F0 的欄位語意**：「跳過」是否也要允許只填活動不填分數？目前活動欄預設 FALSE，可能需要區分「沒做」與「沒填」。
2. **F1 的最小資料量**：一週幾筆才畫點？建議 2，但要看實際 7、8 月的分布。
3. **F3 主動版通道**：email 是 GAS 最省事的通道，但會落入信箱噪音。是否值得接 LINE Notify 或其他？建議 Phase 2 再議。
4. **`.gs` 不在 repo 內**：README 提到 `energy-journal.gs`，但 repo 目前只有 `index.html`。開發前需先把後端程式碼納入版控，否則 F0、F1、F4 的改動無法追蹤。
5. **9/15 檢查點的處置**：若當日仍為 0 筆，除了修正卡片說法，是否直接把 F3 被動版提前？建議仍守 Phase 1 順序，把 0 筆本身當成 A/B 的一部分。

## 10. 對回 Vault 既有機制

| 提案 | 對應層（[[能量日誌的個人改變機制]]） | 補的是什麼 |
|---|---|---|
| F0 跳過標記 | 資料層 | 讓意圖可被記錄 |
| F1 週回顧 | 層 1 可見化 | 密度降低後的聚合補償 |
| F2 補登 | 摩擦 | 一次漏記不等於永遠沒了 |
| F3 提醒 | 層 2 反饋迴圈 | 讓失效會出聲 |
| F4 寫入驗證 | 基礎設施 | 消除系統自己的安靜失效 |

[[為什麼追蹤能量]] 的四個警告中，「不是內疚來源：某天沒記錄，不用補、不用內疚」與 F2 補登、F3 提醒有張力。判準 C2、C3 就是為了守住這條。
